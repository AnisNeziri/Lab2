## Prepare the installation

1. Name one real company and its installation/database. Record deployment mode (server or desktop), timezone, regular working days, holidays, operational cutover date, owner, accountant and support contact in company-controlled documentation. Obtain the actual source files; retain originals and their SHA-256 hashes in Document Center. Never send passwords or bank credentials in feedback.
2. Follow the PR1 release procedure: verified full backup **before** migrations, reopen/verify the archive, retain the previous release and separate key escrow, rehearse restore into an isolated installation, and record integrity totals. Review PR1's remaining hosting/signing/reboot gates and PR2's measured limits. Apply migrations only to the selected installation after its backup and release review. No live migration or business import is performed by this preparation branch.
3. Configure `AIMS_PILOT_COMPANY_ID` for exactly that company. Leave it empty on development, synthetic and other-company installations. Clear/rebuild Laravel configuration cache through the existing release procedure. This setting alone does not enroll a company or enable collection.
4. Open **Administration → Company pilot → Rollout plan**. Save a draft with actual users, responsibilities and daily tasks. Use existing Users/CMS permission administration to inspect actual role permissions. The pilot form never grants access or resets roles, credentials, dashboard layouts or navigation preferences.
5. Demonstrate role tasks below using each employee's own account. Record a `permission_review` observation and independent owner review. A responsibility such as “finance” in the plan is a business label; API permissions still come from the existing role system.
6. Review opening inventory, opening finance where selected, and a separate restore drill with source documents and independent reviewers. Do not mark untested checks confirmed. A more recent failed/unreviewed observation supersedes an old approval. Uploaded documents and human attestations support a review; AIMS cannot prove their real-world authenticity.
7. Obtain owner approval of rollout scope and cutover. Save the plan as active only on a correctly configured production installation, after cutover and required reviews, with a reopened full backup in the last 30 days. Test/demo database markers and known demo accounts block real-data attestation. Do not remove test markers to bypass this check. Establish a clean company installation and migrate only verified business sources.
8. Tell employees about optional aggregate measurement before enabling it. The plan must be active, selected and attested for opt-in collection. State changes take effect within the 60-second server cache; saving the plan invalidates that cache immediately. A browser opened before opt-in reloads to discover the new setting. Pausing on the server stops acceptance even if a browser still shows the old indicator.

Before cutover the agreed legacy system remains authoritative; after cutover only the selected workflows use the agreed AIMS process. Record exceptions explicitly.

## Imports and opening balances

Use `templates/` as source mapping headers, not executable seeds. No example business amounts or identities are included. Export XLSX to UTF-8 comma-separated CSV first. The PR3 preflight deliberately supports CSV only and does not claim to repair the legacy XLSX importer.

Open **Import preflight**, choose the dataset, and review the file. Limits: 5 MB, 10,000 rows, 50 columns, 64 KiB per row; identity scanning stops above 100,000 existing master records. Every parsed data row appears in accepted/rejected totals. Counts include all rows; inline diagnostics show the first 250 and explicitly count omitted details. Split source batches to 250 rows when every row needs inline review. Keep the original file/hash and review record in company storage.

Accepted means structurally reviewable, **not** approved for posting. Required fields, encoding, numeric values, tenant warehouse references and opening SKU/unit matches are checked. Normalized SKU/name/phone/recorded tax IDs identify duplicate candidates in existing masters and in the batch. Candidates are warnings, never auto-merges. Similar names may still require human comparison; this is not exhaustive fuzzy deduplication. A missing supplier tax field is not invented in the supplier model. Missing price/cost, currency conversion, local formatting, regulatory identifiers, location needs and source authority require the relevant domain review.

Use existing product/import, customer/supplier, warehouse, inventory and accounting workflows after preflight. Unsupported bulk operations remain an operator-assisted, separately reviewed import task; the preflight is not a hidden bulk writer. Do not directly update cached product quantities, customer debt, cash or inventory valuation to force totals to match. Preserve domain idempotency, transaction and audit boundaries. Never infer missing bank/cash, customer credit or supplier AP.

Before stock posting reconcile SKU, authoritative unit, warehouse, optional bin/lot, quantity and authoritative unit cost. Immediately compare company/warehouse/location totals and run System Integrity. For finance attach source documents, preparer, reviewer, date, currency and reconciled totals. Finance evidence needs `accounting.reports.view`; the reviewer must be a different authorized person. New evidence records correct an error; approved evidence and review snapshots are append-only.

## Daily and weekly operation

Daily, compare source sales, inventory, customer receivables/advances, cash/bank, active supplier positions and unprocessed tasks. Investigate differences immediately. Record actual reconciliation totals and references in Document Center, then a `daily_reconciliation` observation. Capture a daily review snapshot in the owner workspace. A snapshot contains observed database fields and does not prove external reconciliation.

Each week review sales/orders captured, inventory discrepancies, overdue debt, purchasing/shipment activity, adoption, unresolved data gaps, exceptions and intelligence readiness. Assign missing receipt/PO/date information to purchasing, stock/count/location work to warehouse and debt/cash data to finance. Use **Report a problem** for confusing steps, missing actions, click burden, slowness, terminology, missing data, errors or requests. The owner classifies P0/P1/P2/P3 and records status/resolution. P0/P1 need immediate investigation; P2 is batched. The feedback log does not page an external support team automatically.

Use the existing assistant feedback/correction flow for actual employee questions. Record intent/entity success, clarification, missing evidence, unsupported answers and tool failures as reviewed trials with source references. Follow “No, I meant …” corrections in the same conversation. No unrestricted retraining is introduced. Track real decision accept/modify/dismiss and later outcomes in existing Decision Learning. Start Automation Studio with notifications/review tasks; retain human approval for POs, stock, finance and cancellations. Review usefulness, duplicate suppression, ignored tasks and false alerts; disable noisy rules. Preserve personal layouts and refine role defaults only after evidence.

## Readiness and measurement semantics

The company scorecard uses completed days in the configured timezone, at most the last 90 days. Sales coverage counts finalized sheets on configured ISO weekdays after cutover. A day placeholder or no rows does **not** mean zero sales; unknown business days are listed. Holidays need human calendar review. Current master completeness and historical counts are explicitly distinct from external source coverage. Walk-in customers, stock snapshots, partial-receipt correctness, finance source coverage and pooled live accuracy remain unknown where no defensible denominator/evaluation exists.

Forecast and supplier readiness reads the existing immutable model evidence and calls the existing promotion gates. It never captures observations, trains, promotes or changes thresholds. Inventory still requires 56 observed days, 80% coverage, two validation windows and the existing baseline/incumbent improvement policy. Supplier still requires 40 eligible training outcomes, eight validation outcomes and existing improvement gates. QUALIFIED requires an active model, valid artifact, unchanged gates and attested non-test provenance. Candidate evaluation is not production qualification. Displayed model lists are bounded at 100 per domain; totals disclose truncation. A domain state describes available models, not a certification of every product or supplier. No global MAE/WAPE is made by mixing overlapping windows.

Opt-in metrics store per-company/day/route-template/method/role/status counts and duration histograms. No raw URL/query, body, search term, private document, user timeline or typing is stored. DAU requires a visible navigation signal, deduplicates per user/day and attributes the first role of that day; background polls do not count a user as active. p50 requires 20 samples; p95 requires 100. Values are histogram upper bounds; the >10s tail is unknown. These are PHP response timings including middleware, not full browser task time or CPU measurements. Streamed responses are not materialized for measurement; payload bytes include Content-Length only. Route summaries show the 50 most-used routes. `pilot:prune` runs daily for the explicitly selected company, retaining 90 days of usage aggregates and 30 days of incidents. No raw user activity export is added.

For actual production performance, compare routes and payloads to the PR2 report, including its unmet targets. Capture actual server CPU/RAM/disk, DB connections/size, Redis and queue depth using the deployment's monitoring; note time and configuration. Save daily row counts for movements, journals, analytics snapshots, business events and audit logs in company monitoring records. Estimate growth only from multiple actual observations, not from one fixture. Track real backup size/duration/verification and separate restore duration. Record low sample counts and unavailable observations as unknown.

## Support, backup, failure drills and export

Owners can open **Support → Check health & recent errors** and existing **System Integrity** for version, DB/runtime/worker/backup checks and safe failure codes. Production API exceptions return a server-generated `AIMS-…` reference; logs contain route templates, time, company/user IDs and exception type, without exception messages, bodies, bindings or stacks. The reference is searchable in the selected company's safe incident list; during a DB outage the file log retains it. Existing request IDs remain supported.

Portable company backups now include the pilot plan, feedback, evidence and reports. Authentication remains excluded. Usage/incident telemetry stays under its separate retention policy and is not portable business evidence. A portable restore resets enrollment/consent, cutover, participants and attestation, and marks evidence/reports historical. Historical observations cannot authorize activation or be approved as fresh evidence. Models retain existing archival restore rules. Before a new rollout review the restored business sources and record new local trials. Full installation recovery continues to follow PR1; never overwrite the live database for a pilot drill.

Schedule a controlled restore of an actual company backup into a separate environment outside business activity. Compare inventory, customer/supplier/finance/document integrity totals and retain the signed drill report. If desktop is actually used, record real startup/offline/restart/local-backup consistency. Simulate Internet/service/worker/DB failure only on an approved separate installation or safe maintenance window; record stale/live distinctions, user messaging, recovery and monitoring. No fault injection is performed by this branch. Validate AIS, SMTP, webhooks or other integrations only when actually selected. AIS freshness is the provider's reported position timestamp, not proof of precise live location.

Confirm authorized exports of products, customers, suppliers, orders, inventory, finance and important documents using existing domain exports and portable/encrypted backup. Reopen/read exports in company-controlled storage and validate totals. Record formats, responsible owner and document-file access; a checksum alone is not evidence that employees can use an export.

## Reviews and exit

Capture an actual baseline before any improvement claim. At 30 days review adoption, completeness, P0/P1, stock accuracy, friction and resources. At 60 days review repeat usage, supplier/customer outcomes, maturing forecast windows and decisions. At 90 days decide which workflows are trusted, limited and suitable for primary operation. Minimum observation recommendation: 8–12 weeks; the configured minimum is 56 days. Missing ML qualification is legitimate if clearly communicated.

Exit requires no unresolved P0, reliably used critical workflows, inventory and finance reconciliation, actual restore evidence, reviewed permissions, routine work without developer assistance, materially improved data readiness and acceptable real-use performance. P1 blockers also need explicit disposition before primary use. An `exit` snapshot is a historical capture, not an automatic approval. The owner/accountant signs the source exit review and the final report. This preparation intentionally has no automatic “complete pilot” or “make primary” switch. Choose a next roadmap only after reviewing that evidence; PR3 does not start another phase.
