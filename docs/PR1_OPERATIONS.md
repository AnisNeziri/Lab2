# AIMS PR1 operations and disaster recovery

The authoritative application version, toolchain and supported upgrade baseline are in `RELEASE.json`. This release remains **uncertified** until every required item in `PR1_RELEASE_CHECKLIST.md` passes. Customer data must never be used by certification scripts.

## Supported configurations

Server: one Linux VPS, Nginx, PHP-FPM 8.3.35, MariaDB/MySQL with InnoDB, Redis, Python 3.12.2 with NumPy 2.3.5/SciPy 1.16.2, database queues and systemd. Initial target: Ubuntu 24.04, MariaDB 10.11 LTS or a currently maintained compatible MariaDB release. MySQL 8 compatibility is a design target; it requires its own populated certification before claiming support. Windows desktop: bundled PHP/Python and local React assets, SQLite, database queues, file cache/sessions, explicit loopback origins; Redis is optional and disabled. ARM, macOS, network-share SQLite, multiple writers across hosts and Kubernetes are outside the certified scope.

Build versions: PHP 8.3.35, Composer 2.8.12, Node 22.14.0, npm 10.9.2, Python 3.12.2, Electron 41.10.5. Use Composer and npm lockfiles with `composer install` and `npm ci`. Never run dependency updates during deployment. Windows portable PHP is downloaded by `scripts/download-desktop-php.ps1` and checked against the [official PHP checksum](https://www.php.net/downloads.php?os=windows&osvariant=windows-downloads&version=8.3). Build runtime selection fails on a different PHP/Python version. A customer desktop needs neither XAMPP nor a system Node/Python installation.

Required PHP extensions: bcmath, ctype, curl, dom, fileinfo, mbstring, openssl, PDO, xml, zlib, zip and the selected PDO driver; sqlite3/sodium are included in desktop packaging. Reserve at least 512 MB on each storage filesystem, and at least five times the uncompressed database plus 512 MB during backup. The current full archive is bounded to 512 MiB of raw database/files and uses a 2 GiB backup CLI memory limit. Larger installations need a separately validated streaming backup solution.

## Stage a server

1. Provision a supported patched Linux host and a domain you control. Permit SSH only from administrator networks and public ports 80/443. Bind MariaDB and Redis to loopback; never publish their ports. Install PHP-FPM/extensions, Nginx, MariaDB, Redis, Python 3.12.2, Composer 2.8.12, Node 22.14.0/npm 10.9.2, `gettext-base`, Certbot and the MariaDB command-line tools.
2. Create an `aims` service account and `/srv/aims/{releases,shared}`. Stage the reviewed immutable source at `/srv/aims/releases/<version>`, with `current` pointing to it. Shared directories: `storage/{app/private,app/public,framework/cache/data,framework/sessions,framework/views,logs}`, `documents-private`, `encrypted-backups`. Grant write access only to shared data and each release's `backend/bootstrap/cache`; PHP-FPM must use the same group. Shared directories should be mode 0770, data files 0660 or stricter, secrets 0600. Do not expose `public/storage` or private documents in Nginx.
3. Create a dedicated database and unique DB user with privileges confined to that schema. Use UTC database sessions, InnoDB and `explicit_defaults_for_timestamp=ON`. Back up the database administrator credentials separately. Use a separate network-restricted database migration identity where your operating model allows it.
4. Copy `deploy/production.env.example` to `/srv/aims/shared/production.env`; supply the real HTTPS origin, dedicated DB credentials, unique APP_KEY, protected backup key file and explicit company IANA timezone. Symlink each release's `backend/.env` and `backend/storage` to shared state. Keep `APP_TIMEZONE=UTC`; dates in daily books, debt/payments, accounting reports, procurement and date-based automation use `AIMS_COMPANY_TIMEZONE`. This initial mode assumes one operating company timezone per installation. User display preferences can use another timezone. SMTP is optional; turn on `AIMS_MAIL_ENABLED` only after verifying real SMTP credentials and delivery. Keep file cache/sessions with database queues to allow core business reads/writes to continue during a Redis outage.
5. Generate the APP_KEY once (`php artisan key:generate --force`) and escrow the resulting secret outside the server and outside backup archives. Never regenerate it during upgrade or recovery. Generate a separate random backup passphrase into `/etc/aims/backup-passphrase`, owned by aims, mode 0600. Also escrow the original deployment environment, license/update entitlements and provider credentials in an independent secret store. Archives contain encrypted database secret fields but no plaintext APP_KEY or backup passphrase.
6. Run `composer install --no-dev --classmap-authoritative --no-interaction`. Build React using `npm ci && npm run build`. Create `/srv/aims/venv` with Python 3.12.2 and install `backend/ml/supply_optimizer_requirements.txt` into that interpreter. Set `AIMS_ML_PYTHON` to its absolute executable. Run `php artisan migrate --force` on a **fresh empty database**. Provision a real owner with the existing administration flow; never run the demo DatabaseSeeder in production. Create recovery access with `php artisan users:create-superadmin <real-recovery-email>`; it prompts for a unique password and requires change on first use. Desktop recovery provisioning is offline-only and does not replace a previously chosen password.
7. Run `php artisan optimize:clear`, `config:cache`, `route:cache`, `view:cache`, then `aims:production-check --before-start`. All failures include operator actions. Do not work around a red check. Avoid `env()` outside configuration files when extending the application. Behind Nginx on the same host no trusted proxy is needed; add an explicit proxy allowlist before putting the app behind a separate load balancer. Never trust all forwarded hosts/IPs.
8. Obtain Let's Encrypt certificates using Certbot webroot at `/var/lib/letsencrypt`; bootstrap the HTTP-only virtual host first. Enable `certbot.timer`; run `certbot renew --dry-run`. Render `deploy/nginx/aims.conf.template` with `envsubst '${AIMS_DOMAIN} ${AIMS_ROOT} ${PHP_FPM_SOCKET}'`, so Nginx variables remain intact. Check `nginx -t`, then reload. Match PHP `upload_max_filesize=100M`, `post_max_size=110M`, memory 1 GiB and FPM execution timeout with Nginx. The application enforces its tighter file-type/size rules. API routing goes only through `backend/public/index.php`; SPA fallback and immutable hashed assets are separate. HTTPS redirects and security headers are enabled.
9. Install `deploy/systemd/aims-*` into `/etc/systemd/system`, install `deploy/backup.sh` at `/srv/aims/bin/backup.sh`, `chmod 0750` scripts, `systemctl daemon-reload`. Enable/start `aims-worker@default`, `aims-worker@supply-optimizer`, `aims-worker@strategic-simulation`, `aims-scheduler.timer` and `aims-backup.timer`. For weekly backups adjust the timer's calendar; for manual mode disable the timer. The default backup timer is daily 02:30 UTC. Separate production scheduler processes must not overlap.
10. Require `php artisan aims:production-check` and HTTPS `/api/readiness` to pass. Verify a real owner login, upload/download, inventory receipt, payment, journal and intelligence view, then a backup and separate restore. Reboot the **test server** and verify all enabled workers/timers return automatically before customer approval. Follow the authoritative checklist.

The [Laravel deployment guide](https://laravel.com/docs/12.x/deployment) explains the public web root and caches. The [queue guide](https://laravel.com/docs/12.x/queues) requires retry expiry to exceed worker timeout; AIMS uses retry-after 300 seconds, 240-second optimizer/simulation limits and supervised bounded workers. Keep the service stop timeout at 270 seconds. Logs rotate daily for 14 days. Exclude secret URLs/query strings and document bodies from reverse-proxy and provider logs. Monitor free space, backup recency, failed queues and `/api/readiness`; a missing worker or required Redis/DB/Python returns 503 without secret details. Administrator diagnostics supply safe release, worker, integrity and backup summaries.

## Upgrade from 5db86866

Use the selected `5db86866` database baseline, not an empty migration-only test. Stage and review the next release first, including dependencies and shared-state links. Run `deploy/upgrade.sh /srv/aims/releases/<version>` on an approved maintenance window. It stops writers, creates and authenticates an encrypted full installation backup **before** applying forward migrations, builds release-specific caches, checks startup and switches the application symlink. Old workers stop before schema changes and new workers produce version-specific heartbeats. A failed step leaves maintenance active for investigation.

PR1 adds token-version revocation and removes MariaDB's implicitly updating timestamp attributes while preserving existing column values. Users must log in again after upgrade. Historical migration `reset_admin` no longer overwrites credentials. Forward migrations intentionally have no destructive down operation. If new code fails after migrations, keep writers stopped. Switch back only after checking schema compatibility. If uncertain, restore the pre-upgrade archive to a **separate empty database and attachment root**, reconcile it, point the prior compatible application at the recovered state and verify login/workflows. Never `migrate:rollback`, `migrate:fresh` or reseed the live database as a recovery method.

## Encrypted full backup and independent restore

Full installation backups supplement existing selective company exports. Manual backups remain protected by retention; scheduled backups keep at least two known verified copies (default fourteen). Scheduled backup uses both OS and application locks to prevent overlap, stops writers, validates inventory/finance/attachment/tenant integrity, snapshots SQLite or an InnoDB consistent SQL dump, authenticates the AES-256-GCM archive, validates every checksum, then atomically publishes the archive and its verification sidecar. Files with a stale/invalid sidecar are not counted as known good. A failed backup retains the previous successful timestamp and leaves the maintenance window closed for attention.

On A, stop workers/scheduler and enter maintenance mode. From its backend directory:

```sh
php artisan down --retry=60
php -d memory_limit=2048M artisan aims:installation-backup create --key-file=/etc/aims/backup-passphrase
php -d memory_limit=2048M artisan aims:installation-backup verify --file=/srv/aims/shared/encrypted-backups/<archive>.aimsinstall --key-file=/etc/aims/backup-passphrase
```

Resume A only after successful backup. Copy the authenticated archive and SHA-256 metadata to separate off-server encrypted storage; keep a daily copy and protected monthly/offline copy. Transport access keys must be escrowed separately. Test the actual off-server retrieval at least monthly. A same-disk backup is not disaster protection.

For B, install compatible AIMS with the **same engine**, a separate empty database, empty private/public/document roots and the **original escrowed APP_KEY**. Do not run migrations first. Configure a protected passphrase file outside the backup directory. Keep B in maintenance with all workers stopped, then:

```sh
php artisan down --retry=60
php -d memory_limit=2048M artisan aims:installation-backup restore --file=<absolute-retrieved-archive>.aimsinstall --key-file=/etc/aims/backup-passphrase
php artisan documents:verify <company-id>
php artisan aims:production-check --before-start
```

Restore verifies authentication, archive/version compatibility and database integrity before activation, runs compatible forward migrations, restores actual bytes and compares every inventory/financial control total. It rejects populated targets, engine mismatch, incompatible future versions, wrong keys and corruption. An incomplete restore leaves `storage/framework/aims-restore-incomplete`; discard the incomplete scratch target and retry into another empty B. Never remove the marker to bypass validation. Current version compatibility: archive format 1, application versions 1.0.0 through the installed release, same engine only; older data is migrated forward. Selective company transfer is a different workflow.

Pre-loss access/refresh/reset/API tokens, sessions and queued jobs are invalidated. Automations, integration providers, webhooks and order channels are disabled, pending external retries cancelled and channel keys revoked. Review integrations, rotate external credentials and explicitly reenable only after confirming that A is offline. Do not allow A and B to process the same business concurrently. Review licence binding/update channels on a replacement desktop. Verify owner login, settings/preferences, intelligence history, each attachment association, inventory and six finance controls in System Integrity. Start workers, require full readiness, then reopen. Record the operator, archive hash, restore time and comparisons.

## Recovery by incident

Database corruption: stop all writers, preserve the damaged DB and SQLite WAL/SHM files together for investigation; verify and restore the last retrieved known-good archive into B. Lost server: provision a fresh host and execute B recovery with escrowed secrets. Lost desktop: install the reviewed signed installer on a replacement Windows computer, recover license entitlement via the existing licensing process, recover original APP_KEY independently and restore B; licence signing keys never travel with customers. Failed upgrade: use the pre-migration archive and prior application as above. Broken configuration: keep data untouched, restore the escrowed environment/APP_KEY, clear/rebuild caches, run readiness before restarting. Lost attachment directory: stop writes and restore an entire matching installation snapshot into B; compare DB document versions to actual restored checksums. Do not mix an old attachment directory with a newer live DB.

If keys are lost, authenticated encrypted backups cannot be recovered by guessing or resetting APP_KEY. Maintain independent tested escrow. Recovery target: daily backup implies up to 24-hour data loss; measured restore time is environment-specific, not a promised SLA. Failures, reconciliation mismatches, missing attachments and cross-tenant results block reopening.

## Exports, limitations and support

Existing CSV/data/report exports and selective encrypted company backups remain available. Complete installation restore preserves supported tables/files, including preferences/settings/intelligence history. It is administrator disaster recovery, not a per-tenant self-service export. A company-wide portable export still has module coverage limits and does not replace a full backup. Document custom integrations/export omissions before onboarding.

Supplier ML remains unpromoted; predictive outcome history is insufficient for broad accuracy claims. AIS/carrier availability depends on separately configured providers. Tax/fiscal integration and real carrier accounts are not certified by synthetic tests. Local certification measures representative PM3 data, not multi-company scale or a latency SLA. A clean bundled startup test does not establish installer signing, fresh-VM installation, licence activation or a real VPS reboot. These are explicit checklist requirements before customer release.
