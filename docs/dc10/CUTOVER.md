# Separately approved MariaDB cutover — not executed

This procedure is a preparation document. DC10 authorizes isolated recovery, not changing the active database connection. Do not use the rehearsal schema containing access quarantine and disposable company 8 as the live candidate.

1. **Prerequisites and approval.** Name the operator, DBA/reviewer, maintenance window, final decision maker and rollback deadline. Record unresolved opening/certification blockers explicitly. For live-company operation require independently approved source statements, financial reconciliation and the existing DC8 encrypted installation restore drill. Stop if a prerequisite fails. Database-only migration must never be described as financial or commercial readiness.
2. **Preserve inputs.** Retain the original MariaDB installation/data, existing DC9 cold copy, source configuration, application version, documents, protected original APP_KEY and installation identity. Confirm restricted access and separately escrow the key according to DC8. Verify hashes and available disk space; copying a file without verifying it is insufficient.
3. **Freeze writers.** Put AIMS into maintenance for the approved window. Stop/drain workers, scheduler, desktop/offline synchronization, integrations and other database writers. Record the last accepted transaction/time. Keep the source available for export without further business writes. Do not repair its grant/system tables.
4. **Final consistent snapshot.** Generate a new logical export with `--single-transaction --quick --hex-blob --skip-lock-tables --routines --events --triggers`, business schema only. All current tables are InnoDB; recheck this before relying on transaction consistency. Hash the SQL, record export start/end, table/object inventory, migration history and source financial/stock/tenant fingerprints. Copy/hash documents and key/identity inputs at the same cutoff. Recheck source freshness after export; any unexplained write requires a new snapshot.
5. **Fresh candidate.** Use a separately named empty schema on the supported installation, never overwrite the source or reuse a tested schema. Restore business objects only; inspect any future view/routine/event/trigger definers and privileges independently. Retain strict SQL modes, UTC and source table/column collations. Do not import `mysql` or other system schemas. Create reviewed runtime, migration and backup identities scoped to this candidate. Inspect effective roles/PUBLIC grants as well as direct grants. Keep external delivery/scheduled events disabled until approved.
6. **Verify before switching.** Match all tables, rows/fingerprints, indexes, foreign keys, CHECK constraints and other objects, stock/reservations, AR/AP/advances, cash/bank, journal and payroll history, documents/references and tenant ownership. Verify key witness, encrypted providers and installation identity with the original key. Run migration status first; use only the migration identity for any reviewed pending migrations. Exercise runtime reads/writes with a disposable tenant in a separate validation copy; never insert synthetic records into the live candidate. Check runtime forbidden access, restarts, worker/scheduler connectivity, backup/export and restoration. Stop on a mismatch.
7. **Configuration switch after explicit approval.** Preserve the active configuration securely. Set host/port/schema and the dedicated runtime credential; keep the original APP_KEY and installation identity. Keep migration/backup credentials out of everyday runtime configuration. Rebuild configuration cache if used and restart API/desktop clients and long-lived workers so old connection pools cannot keep writing to the source. No source/candidate may accept parallel business writes.
8. **Smoke checks while restricted.** Confirm the actual connected version, database and runtime user; normal authentication, tenant access, authoritative stock/finance reads, opening status and documents. Check a one-shot worker and scheduler initialization without releasing queued external financial/fiscal/payment actions. Verify a fresh backup. Show separate SQL, encrypted-restore and financial gates. Only the approved operator may record that an active cutover actually occurred; the DC10 rehearsal receipt has this flag false.
9. **Release or rollback.** Before the first new business write, failed smoke checks permit reverting the saved connection configuration and restarting processes against the preserved source. After new writes on the candidate, stop all writers and reconcile/export the delta under DBA/accountant control; never blindly switch back and lose transactions. Record the decision and the authoritative database.
10. **Retain evidence.** Preserve the old instance and final snapshot unchanged for investigation/rollback. Do not delete legacy grant data or guess the two unidentified rows. Retain verification logs, cutoff/freshness evidence, approval and rollback decision. Resume workers/integrations gradually only after their policies and readiness gates pass.
