# Operator handoff — pending evidence and approval

This is a preparation procedure. No production connection change or real-company pilot is authorized by a test result. Preserve the original installation until retirement is separately approved. Continue using the [DC10 cutover steps](../dc10/CUTOVER.md), with these additional prerequisites.

1. **DBA/source review.** Review the 13 foreign-key violations in `output/dc11-source-reference-audit.json`. Distinguish missing business parents, audit actors and obsolete authorization mappings. Preserve original rows and explain any proposed correction. Do not recreate users, POs, permissions or grants merely to satisfy a constraint. Table checksums must still match before approved corrections; afterwards record the approved delta and validate all references and tenant ownership. The rehearsal demonstrates why parent-ID reuse can attach old history to a new record. Its failed synthetic PO is preserved/cancelled, not suitable as production data.
2. **Accountant source pack.** Agree the cutoff date, timezone and base currency. Obtain independently reviewed trial balance/equity, customer statements/invoice attribution, supplier statements and actual payment currencies/rates, inventory quantities/cost evidence, bank statements and cash counts. Attach genuine files in Document Center and match them to existing records. AR, supplier advances, inventory and cash remain blocked until justified corrections are approved and posted through existing services. Do not import existing history again through DC1. A zero GL, review note or configured opening date is not approval.
3. **Encrypted restoration.** Use `aims:installation-backup create`, `verify` and `restore`, with `--key-file` pointing to the protected archive-passphrase file. APP_KEY is a separate escrow input and is never included in the archive. Restore only into a new empty installation and empty file roots. Review archive integrity, decryption, database, application-key witness, files and business reconciliation separately. Never remove an incomplete-restore marker to declare success. Old timestamp-only health files do not satisfy the new scoped six-stage proof. After restoration, pilot observations are historical and active pilot plans are paused; obtain new local review and authorization.
4. **Separate operator identities.** Existing runtime grants remain DML only. For MariaDB object-complete backup, the existing service accepts `AIMS_BACKUP_DB_USERNAME` and `AIMS_BACKUP_DB_PASSWORD_FILE`. Restore can use `AIMS_RESTORE_DB_USERNAME` and `AIMS_RESTORE_DB_PASSWORD_FILE`. Supply these only to the authorized backup/restore process, using ACL-protected credential files; keep restore administration out of everyday web runtime configuration. These files differ from both APP_KEY escrow and the archive passphrase. Set the verified MariaDB 11.4 client paths through `AIMS_MYSQLDUMP` / `AIMS_MYSQL`. Recreate reviewed schema-scoped grants for the fresh candidate; do not copy system tables or elevate the runtime account. Pending migrations require the existing migration identity/workflow.
5. **Maintenance and cutover approval.** Once prerequisites pass, name the operator, reviewer, maintenance window and rollback deadline. Stop all writers/workers/scheduler/integrations; take a new consistent SQL and file snapshot, hash it and verify no later source writes occurred. Restore a **fresh candidate**, compare tables/objects, references, tenants, stock, finance, files and key/identity, then establish a backup checkpoint. Change the active connection only after explicit approval. Keep the old source preserved. Before new writes, failed smoke checks permit reverting the saved configuration. After new writes, stop and reconcile the delta; never blindly switch back and lose transactions.
6. **Process commissioning.** Configure the existing supervisors for default, supply-optimizer and strategic-simulation workers plus the existing scheduler. Review release-specific heartbeats, failed jobs, actual outage/recovery and connection recovery. A one-shot worker, scheduler list or manually generated heartbeat is not proof of supervision. Review queued external work before releasing it; uncertain payment/fiscal results require authorized verification rather than blind retries. Retain the last verified backup, original key and audit/request references during an incident.
7. **Pilot scope / human authorization.** Prepare the existing pilot plan with actual participants, responsibilities, business days and workstreams. Review users/roles, warehouses, products/units, customers, suppliers, accounts and stock opening without fictitious records. Record `Commissioning scope` in Pilot Evidence with a real supporting report and checks named **Fiscalization scope**, **Payroll scope**, **Runtime security commissioning**. A different authorized person reviews it. Explicitly document scope exclusions; generic integration evidence or empty tables do not establish exclusion. Complete independent opening-finance, stock, role, restore and server-drill evidence. Operator selection through `AIMS_PILOT_COMPANY_ID` and owner activation remain explicit production actions. The checklist does not grant authority.
8. **Security/release decision.** Resolve/re-audit DC8 desktop findings before desktop distribution. Review signing, HTTPS/passkey identity, trusted issuer keys, host controls and off-device recovery escrow. A scoped web pilot cannot certify Electron distribution, fiscalization, payroll or commercial deployment. Stop and report any unresolved prerequisite; do not start DC12 automatically.
